# Packer Plugin SIMH — Implementation Specification

## 1. Overview

This document specifies a Hashicorp Packer builder plugin for the
[SIMH](https://opensimh.org) historical computer emulator. SIMH
simulates dozens of classic computers (VAX, PDP-11, Altair, IBM 7094, …). Unlike
QEMU-based builders that communicate with the VM through VNC, this plugin drives
SIMH through **command files** for device configuration and a **telnet
connection** to the simulated console for interactive boot sequences. The
telnet-based console interaction uses the Packer SDK's `bootcommand` parser for
keystroke syntax (e.g. `<enter>`, `<wait5>`) combined with expect-style pattern
matching on console output for reliable synchronisation. The design is modelled
closely on the
[packer-plugin-qemu](https://github.com/hashicorp/packer-plugin-qemu)
architecture.

### Terminology

| Term | Meaning |
|------|---------|
| **SIMH command file** | A text file of SCP (Simulator Control Program) commands passed as a positional argument when invoking a SIMH simulator binary. |
| **SCP command** | Any command recognised by the SIMH console (e.g. `SET CPU 128M`, `ATTACH RQ0 disk.dsk`, `BOOT CPU`). |
| **Simulated console** | The virtual terminal of the emulated machine (e.g. the VAX console terminal). SIMH can expose this over telnet via `SET CONSOLE TELNET=<port>`. Characters sent to the telnet connection are received by the guest OS; characters output by the guest appear in the telnet session. This is distinct from the SCP command prompt. |
| **boot_steps** | An ordered list of `[expect, send, description]` tuples. The plugin connects to the simulated console via telnet, waits for console output matching the expect pattern, then sends the text (parsed using the Packer SDK's `bootcommand` syntax). |

### Naming

| Item | Value |
|------|-------|
| Go module | `github.com/cross-platform-actions/packer-plugin-simh` |
| Plugin binary | `packer-plugin-simh` |
| Builder name (HCL `type`) | `simh` |
| Builder ID | `simh.simh` |
| Initial version | `0.1.0-dev` |

## 4. Plugin Entry Point (`main.go`)

```go
func main() {
    pps := plugin.NewSet()
    pps.RegisterBuilder(plugin.DEFAULT_NAME, new(simh.Builder))
    pps.SetVersion(version.PluginVersion)
    if err := pps.Run(); err != nil {
        fmt.Fprintln(os.Stderr, err.Error())
        os.Exit(1)
    }
}
```

`version/version.go` initialises `PluginVersion` via
`pluginVersion.InitializePluginVersion("0.1.0", "dev")`.

### 5.1 Embedded SDK Configs

The `Config` struct embeds the following SDK types (all with
`mapstructure:",squash"`):

| Embedded type | Provides |
|---------------|----------|
| `common.PackerConfig` | `packer_build_name`, `packer_debug`, `packer_force`, … |

### 5.2 SIMH-specific Config Fields

Fields are listed with their HCL key, Go type, default value, and description.

#### Simulator Binary

| HCL key | Go type | Required | Description |
|---------|---------|---------|-------------|
| `simh_binary` | `string` | **yes** | Name or path of the SIMH simulator binary. Resolved via `exec.LookPath` at the start of `Run()`, not during `Prepare()` (see §5.5 and §8). |

#### Output

| HCL key | Go type | Default | Description |
|---------|---------|---------|-------------|
| `output_directory` | `string` | `"output-<BuildName>"` | Directory for all build outputs (disk images, command file, logs). Removed on `--force`. |
| `vm_name` | `string` | `"packer-<BuildName>"` | Base name for generated files (command file, log file). |

#### CPU & Memory

| HCL key | Go type | Default | Description |
|---------|---------|---------|-------------|
| `cpu_type` | `string` | `""` | Passed as `SET CPU <cpu_type>` if non-empty. Example: `"MicroVAX"`. |
| `memory` | `string` | `""` | Passed as `SET CPU <memory>` if non-empty. Example: `"128M"`. |
| `cpu_options` | `[]string` | `[]` | Additional `SET CPU` operands. Each generates a separate `SET CPU <value>` line. Example: `["CONHALT", "64"]`. |

#### Disk Attachments

| HCL key | Go type | Default | Description |
|---------|---------|---------|-------------|
| `disk_attachments` | `[]DiskAttachment` | `[]` | List of disk/tape device attachments. |

`DiskAttachment` struct:

| Field | HCL key | Go type | Required | Description |
|-------|---------|---------|----------|-------------|
| `Device` | `device` | `string` | **yes** | SIMH device-unit identifier, e.g. `"RQ0"`, `"RL0"`, `"TQ0"`. |
| `Path` | `path` | `string` | **yes** | Path to the image file. **Contains runtime template variables** — interpolated at command file generation time (see §5.3). Relative paths are resolved from `output_directory`. |
| `Options` | `options` | `string` | no | Additional SIMH ATTACH options, appended after the path. |
| `SetCommands` | `set_commands` | `[]string` | no | `SET <device> <value>` commands to emit *before* the ATTACH. Each string is the operand to `SET <device>`. |

Example HCL:

```hcl
disk_attachments {
  device       = "RQ0"
  path         = "{{ .OutputDir }}/system.dsk"
  set_commands = ["RD54"]
}

disk_attachments {
  device  = "RQ3"
  path    = "{{ .ISOPath }}"
  options = "-r"
}
```

Generated SIMH commands:

```
SET RQ0 RD54
ATTACH RQ0 output-build/system.dsk
ATTACH RQ3 /path/to/downloaded.iso -r
```

#### Network Configuration

| HCL key | Go type | Default | Description |
|---------|---------|---------|-------------|
| `network_device` | `*NetworkDevice` | `nil` | Optional structured network device configuration. |
| `network_commands` | `[]string` | `[]` | Raw SIMH SCP commands for network setup, appended after any structured network config. **Contains runtime template variables** — interpolated at command file generation time. |

`NetworkDevice` struct:

| Field | HCL key | Go type | Required | Description |
|-------|---------|---------|----------|-------------|
| `Device` | `device` | `string` | **yes** | SIMH network device name, e.g. `"XQ"`. |
| `MAC` | `mac` | `string` | no | MAC address. Generates `SET <device> MAC=<mac>`. |
| `AttachType` | `attach_type` | `string` | **yes** | SIMH attach argument. **Contains runtime template variables** — e.g. `"nat:tcp={{ .HostPort }}:10.0.2.15:22"`. |
| `SetCommands` | `set_commands` | `[]string` | no | Additional `SET <device> <value>` commands. |

#### Boot Steps

| HCL key | Go type | Default | Description |
|---------|---------|---------|-------------|
| `boot_steps` | `[][]string` | `[]` | Ordered list of `[expect, send, description]` tuples (see below). **Contains runtime template variables** — interpolated at `stepBootCommand` execution time. |
| `boot_wait` | `time.Duration` | `"10s"` | Delay after SIMH starts before connecting to the console telnet port. Gives the simulator time to initialise and begin listening on the telnet port. |
| `boot_key_interval` | `time.Duration` | `"0s"` | Minimum interval between keystrokes sent to the console. The SDK's `bootcommand` parser honours this between each key event. Set to e.g. `"50ms"` if the guest drops characters at full speed. |
| `boot_step_timeout` | `time.Duration` | `"5m"` | Maximum time to wait for each individual expect pattern to match. If a pattern does not appear within this timeout, the step fails and the build is halted. |

Boot steps are **not** written into the SIMH command file. Instead, they are
executed at runtime by `stepBootCommand`, which connects to the simulated
console via the telnet port configured by `stepConfigureConsole` and
interacts with the guest directly.

Each boot step is a **3-element string array** `[expect, send, description]`:

| Element | Description |
|---------|-------------|
| `expect` | A substring to match in the console output. The step reads console output until this string appears. If empty (`""`), the send text is dispatched immediately without waiting. |
| `send` | Text to send to the console, parsed using the Packer SDK's `bootcommand` syntax. Supports `<enter>`, `<esc>`, `<tab>`, `<wait>`, `<wait5>`, `<wait10s>`, `<leftCtrl>`, literal characters, etc. — the full set of expressions from `bootcommand.GenerateExpressionSequence()`. |
| `description` | Human-readable label logged to the Packer UI. |

**How `expect` matching works**: The step accumulates console output in a
buffer. For each boot step with a non-empty `expect` string, it reads from
the telnet connection and appends to the buffer until the `expect` substring
is found (using `strings.Contains`). The buffer is **not** cleared between
steps — output from previous steps remains visible for matching. If
`boot_step_timeout` expires before the pattern is found, the build fails.

**How `send` works**: After the expect pattern matches (or immediately if
expect is empty), the send text is parsed via
`bootcommand.GenerateExpressionSequence(send)` and executed through a
`telnetDriver` implementing the SDK's `BCDriver` interface. The driver writes
characters directly to the telnet connection. Special keys are mapped to
control characters / escape sequences appropriate for a text terminal (see
§10.8 for the mapping).

Example HCL:

```hcl
boot_steps = [
  ["", "BOOT CPU<enter>", "Boot the processor"],
  ["Username:", "SYSTEM<enter>", "Log in as SYSTEM"],
  ["Password:", "MANAGER<enter>", "Enter password"],
  ["$", "@SYS$SYSTEM:SHUTDOWN<enter>", "Initiate shutdown"],
  ["SHUTDOWN", "YES<enter>", "Confirm shutdown"],
]
```

**Note on the first step**: The first step has an empty expect pattern,
so `BOOT CPU<enter>` is sent immediately after connecting to the console.
This is a SIMH SCP command that boots the simulated processor. The `BOOT`
command is included in the SIMH command file (generated by
`stepCreateCommandFile`) rather than sent via the console — see §9.4
Section 8. The first boot step with an empty expect can be used for
initial console input if the simulator is already booted.

Example HCL (with boot command in command file, boot_steps for OS interaction):

```hcl
# The SIMH command file includes "BOOT CPU" as part of device setup.
# boot_steps handles the interactive OS prompts via the console.
boot_steps = [
  [">>>", "BOOT DUA0<enter>", "Boot from DUA0 at VMB prompt"],
  ["Username:", "SYSTEM<enter>", "Log in as SYSTEM"],
  ["Password:", "MANAGER<enter>", "Enter password"],
  ["$", "@SYS$SYSTEM:SHUTDOWN<enter>", "Initiate shutdown"],
  ["SHUTDOWN", "YES<enter>", "Confirm shutdown"],
]
```

#### External Command File

| HCL key | Go type | Default | Description |
|---------|---------|---------|-------------|
| `command_file` | `string` | `""` | Path to an external SIMH command file. If set, this file is used **instead** of generating one from structured config fields (see §9.3 for which fields still apply). The **path itself** is interpolated during Pass 1 only — Packer built-in functions (`{{ user }}`, `{{ env }}`, etc.) work, but runtime variables (`{{ .ISOPath }}`, etc.) do **not**. The **file contents** are interpolated during Pass 2 with full runtime variables. |

#### Console Configuration

| HCL key | Go type | Default | Description |
|---------|---------|---------|-------------|
| `console_port_min` | `int` | `4000` | Minimum port for the Telnet console. |
| `console_port_max` | `int` | `4100` | Maximum port for the Telnet console. |
| `console_bind_address` | `string` | `"127.0.0.1"` | Bind address for the Telnet console. Not validated by the plugin — passed directly to SIMH's `SET CONSOLE TELNET=<addr>:<port>`. Invalid values will cause SIMH to error at runtime (visible in the Packer log). |
| `console_log` | `bool` | `true` | Capture console output to a `<vm_name>.console.log` file in `output_directory`. Uses SIMH's `SET CONSOLE LOG=<path>` command. |

The simulated console telnet port is **always enabled**. The plugin:
1. Finds an available port in `[console_port_min, console_port_max]`.
2. Inserts `SET CONSOLE TELNET=BUFFERED=<bind_address>:<port>` and optionally
   `SET CONSOLE LOG=<path>` into the command file.
3. Logs the Telnet address to the Packer UI so the user can connect manually
   for debugging.

The `BUFFERED` mode is critical: it allows the SIMH simulator to run even when
no telnet client is connected. Without `BUFFERED`, SIMH would block waiting for
a telnet connection before executing any commands. With `BUFFERED`, the
simulator starts immediately, console output is stored in an internal buffer,
and when the plugin's `stepBootCommand` connects, any buffered output is
replayed.

**Portability note**: `SET CONSOLE TELNET` and `SET CONSOLE LOG` are standard
SCP commands available in all SIMH simulator builds. If a specific simulator
build lacks support (e.g. a stripped-down custom build), SIMH will print an
error and the command file will abort. The plugin does **not** attempt to
detect or recover from this — the SIMH process error output (captured to the
Packer log) will indicate the problem.

#### Communicator Host/Port

| HCL key | Go type | Default | Description |
|---------|---------|---------|-------------|
| `comm_host` | `string` | `""` | Override the host address used by the SSH communicator to reach the guest. If empty, defaults to `"127.0.0.1"`. |
| `host_port_min` | `int` | `2222` | Minimum host port for SSH forwarding. The plugin selects an available port in this range (see §10.5 `stepForwardPort`). |
| `host_port_max` | `int` | `4444` | Maximum host port for SSH forwarding. |
| `skip_port_forward` | `bool` | `false` | If true, skip host port selection entirely. The communicator will use the guest's configured port directly (e.g. when using bridged networking where the guest IP is directly reachable). |

#### HTTP IP Discovery

| HCL key | Go type | Default | Description |
|---------|---------|---------|-------------|
| `http_ip` | `string` | `""` | Override the IP address the guest should use to reach Packer's HTTP server. If empty, defaults to `"10.0.2.2"` (standard NAT gateway) when `network_device` uses NAT, or falls back to `"127.0.0.1"`. |

#### Extra SIMH Commands

| HCL key | Go type | Default | Description |
|---------|---------|---------|-------------|
| `simh_args` | `[]string` | `[]` | Additional raw SCP commands inserted into the command file **before** disk attachments. **Contains runtime template variables** — interpolated at command file generation time. |

#### Shutdown

| HCL key | Go type | Default | Description |
|---------|---------|---------|-------------|
| `shutdown_timeout` | `time.Duration` | `"5m"` | Maximum time to wait for the SIMH process to exit after all steps complete. If exceeded, the process is killed. |

**How SIMH exits**: The SIMH command file always ends with `QUIT` (appended
automatically by `stepCreateCommandFile`). After all device configuration and
the `BOOT` command, SIMH enters the simulator run loop and the command file
effectively blocks at the `BOOT` command until the simulated CPU halts. When
the CPU halts (e.g. after OS shutdown), control returns to the SCP and the
next command (`QUIT`) executes, causing SIMH to exit cleanly. If the CPU
never halts, `stepShutdown` will kill SIMH after `shutdown_timeout` expires
and fail the build.

### 5.3 Two-Pass Template Interpolation

The plugin uses a **two-pass interpolation** strategy, matching the pattern used
by the QEMU plugin:

#### Pass 1 — `Prepare()` time (via `config.Decode`)

`config.Decode()` is called with `Interpolate: true`. This resolves Packer
built-in template functions (`{{ user "var" }}`, `{{ env "VAR" }}`,
`{{ timestamp }}`, `{{ uuid }}`, etc.) in all config fields **except** those
that contain runtime template variables.

The following fields are **excluded** from Pass 1 interpolation via
`InterpolateFilter.Exclude`:

- `boot_steps`
- `disk_attachments`
- `network_device`
- `network_commands`
- `simh_args`

Note: `command_file` is **not** excluded — its path is interpolated during
Pass 1 (so `{{ user "cmd_file" }}` and `{{ env "CMD_FILE" }}` work in the
path). Only the file's **contents** are interpolated during Pass 2 (in
`stepCreateCommandFile`).

**Why `network_device` must be listed explicitly**: The SDK's
`InterpolateFilter.Exclude` operates on **top-level mapstructure keys only**.
It does not support dot-path notation or recursive key matching. When a
top-level key is excluded, the entire subtree (all nested fields) is skipped.
For example, excluding `"disk_attachments"` skips all `DiskAttachment` fields
(`device`, `path`, `options`, `set_commands`). Similarly, excluding
`"network_device"` skips all `NetworkDevice` fields (`device`, `mac`,
`attach_type`, `set_commands`). Each top-level key that may contain runtime
template variables must be listed separately — `network_device` is a distinct
top-level key from `disk_attachments` and requires its own exclusion entry.

**Why these fields are excluded**: They may contain `{{ .ISOPath }}`,
`{{ .HTTPIP }}`, `{{ .HTTPPort }}`, `{{ .HostPort }}`, `{{ .SSHPublicKey }}`,
etc. — values that are only available at runtime. If `config.Decode` tried to
evaluate them during `Prepare()`, Go's `text/template.Execute` would fail with
an unresolvable field error. Note that excluded fields are still **validated**
(parsed for template syntax errors) during Pass 1 — only execution/rendering
is skipped.

All other fields (e.g. `simh_binary`, `output_directory`, `vm_name`,
`iso_url`, `console_port_min`, `comm_host`) are interpolated during Pass 1.
Packer built-in functions (`{{ user }}`, `{{ env }}`, `{{ timestamp }}`, etc.)
work in these fields.

#### Pass 2 — Runtime (multiple steps)

At runtime, `stepCreateCommandFile` and `stepBootCommand` each populate a
`templateData` struct with runtime values and call `interpolate.Render()` on
the fields they are responsible for. Both Packer built-in functions **and**
the `.Field` runtime variables are available in this pass.

- **`stepCreateCommandFile`** interpolates: `disk_attachments`,
  `network_device`, `network_commands`, `simh_args`, and the contents of
  `command_file` (if set).
- **`stepBootCommand`** interpolates: `boot_steps` (the expect and send
  elements of each tuple).

**Implementation in `config.go`**:

```go
err := config.Decode(&c, &config.DecodeOpts{
    PluginType:         BuilderId,
    Interpolate:        true,
    InterpolateContext:  &c.ctx,
    InterpolateFilter: &interpolate.RenderFilter{
        Exclude: []string{
            "boot_steps",
            "disk_attachments",
            "network_device",
            "network_commands",
            "simh_args",
        },
    },
}, raws...)
```

### 5.5 Validation Rules (`Prepare()`)

The `Prepare()` method must:

1. Call `config.Decode()` with the interpolation settings described in §5.3.
2. Validate that `communicator` type is `"ssh"` or `"none"`. If
   `"winrm"` is set, return an error: `"WinRM communicator is not supported
   by the SIMH builder"`.
3. Call `Prepare()` on each embedded config (`ISOConfig`, `HTTPConfig`,
   `communicator.Config`). **For `ISOConfig`**: if `iso_url` and `iso_urls` are
   both empty, skip calling `ISOConfig.Prepare()` and set a flag
   `isoSkipped = true` (ISO is optional — see §5.6).
4. Validate that `simh_binary` is non-empty (it is required, with no default).
    Set defaults for `output_directory` (`"output-<BuildName>"`), `vm_name`
    (`"packer-<BuildName>"`). Then convert
   `output_directory` to an absolute path via `filepath.Abs()`. This ensures
   `{{ .OutputDir }}` always expands to an absolute path in templates, and
   `cmd.Dir` in the driver is always absolute.
5. Validate that each `DiskAttachment` has both `device` and `path` set.
6. Validate that `NetworkDevice` (if set) has `device` and `attach_type`.
7. Validate port ranges: `console_port_min` <= `console_port_max`,
   `host_port_min` <= `host_port_max`.
8. Check if `output_directory` exists. If it does and `packer_force` is **not**
   set, return an error. **Do not delete** the directory in `Prepare()` — the
   `stepPrepareOutputDir` step handles deletion (§10.1).
9. Validate that `boot_steps` entries are 3-element string arrays
   (`[expect, send, description]`).
10. If `command_file` is set, validate the file exists and is readable.
11. Collect and return all errors, warnings, and the list of generated variable
    names. The generated variable names are returned as `[]string{"ID", "Host",
    "Port", "SSHPublicKey"}`.

`Config.Prepare()` signature:

```go
func (c *Config) Prepare(raws ...interface{}) ([]string, []string, error)
//                                              ^ generatedVars  ^ warnings
```

**Note on `simh_binary` validation**: `Prepare()` does **not** validate that
`simh_binary` exists on `$PATH`. Following the QEMU plugin's pattern, binary
resolution via `exec.LookPath` happens at the start of `Builder.Run()` when
creating the driver (see §8). This avoids false failures during `Prepare()`
on machines where the binary isn't installed (e.g. CI systems that only
validate configs). The `Driver.Verify()` method is called immediately after
`exec.LookPath` in `Run()` for any additional driver-level validation.

### 5.6 ISO Download Conditionality

The ISO download step (`StepDownload`) is **conditional**:

- If `iso_url` or `iso_urls` is configured, `StepDownload` runs normally and
  stores the downloaded path in state as `iso_path`.
- If neither is configured, the step is **skipped** (use `multistep.If()`).
  The `iso_path` state key will not be set. The `{{ .ISOPath }}` template
  variable resolves to an empty string `""`.

This allows builds that use pre-existing disk images (provided via
`disk_attachments` with absolute paths) without requiring a download.

### 5.7 Generated Variables

The builder declares these generated variables (returned from `Prepare()`):

- `ID` — always `"VM"`
- `Host` — communicator host (from `comm_host` or `"127.0.0.1"` when
  communicator is `"none"`)
- `Port` — communicator port. When `skip_port_forward` is true, this is the
  guest port from `communicator.Config.Port()`. When communicator is `"none"`,
  this is `0`.
- `SSHPublicKey` — generated SSH public key (empty string if communicator is
  not `"ssh"` or key generation hasn't happened yet at `Prepare()` time)

## 7. Driver Interface (`driver.go`)

The `Driver` interface abstracts SIMH process management, enabling testing with
a mock implementation.

```go
type Driver interface {
    // Simh launches the SIMH binary with the given command file path.
    // The binary is started asynchronously. Returns an error only if the
    // process fails to start or exits within 2 seconds with a non-zero code.
    // An exit within 2 seconds with code 0 is treated as SUCCESS (not an
    // error) — this handles command files that legitimately complete quickly
    // (e.g. a script that runs and QUITs immediately).
    Simh(commandFile string) error

    // WaitForShutdown blocks until the SIMH process exits or the cancel
    // channel is closed. Returns true if the process exited on its own.
    WaitForShutdown(cancelCh <-chan struct{}) bool

    // Stop forcefully kills the SIMH process.
    Stop() error

    // Verify validates that the SIMH binary exists and is executable.
    Verify() error

    // Version returns the SIMH simulator version string.
    Version() (string, error)
}
```

### `SimhDriver` struct

```go
type SimhDriver struct {
    SimhPath string          // Resolved absolute path to the SIMH binary
    vmCmd    *exec.Cmd       // Running process
    vmEndCh  <-chan struct{}  // Closed when process exits
    exitCode int             // Process exit code
    lock     sync.Mutex
}
```

### `SimhDriver.Simh(commandFile string) error`

1. Build the command: `exec.Command(d.SimhPath, commandFile)`.
2. Set `cmd.Dir` to `filepath.Dir(commandFile)`. Since the command file is
   always written to `<output_directory>/<vm_name>.simh` (see §9), this
   resolves to `output_directory`. This ensures relative paths in SIMH ATTACH
   commands resolve from the output directory. When an external `command_file`
   is used, it is copied into `output_directory` before execution (§9.3), so
   the working directory is still `output_directory`. The `SimhDriver` struct
   does not need an `output_directory` field — the working directory is
   derived from the `commandFile` argument.
3. Pipe `stdout` and `stderr` through a log reader that forwards each line to
   Packer's log (via `log.Printf`), same pattern as `QemuDriver.Qemu()`.
4. Call `cmd.Start()`.
5. Start a goroutine that calls `cmd.Wait()`, captures the exit code, and
   closes `vmEndCh`.
6. Wait up to 2 seconds:
   - If the process exits with **non-zero** in that window → return an error.
   - If the process exits with **zero** in that window → return nil (success;
     the command file completed quickly).
   - If the process is still running after 2 seconds → return nil (normal
     async operation).

### `SimhDriver.Stop() error`

1. Send `SIGTERM` to the process (on Unix) or `Process.Kill()` on Windows.
2. Wait up to **5 seconds** for the process to exit.
3. If still running after 5 seconds, call `Process.Kill()` (force kill).
4. Return any error from the kill operation. If the process already exited,
   return `nil`.

### `SimhDriver.Verify() error`

Perform any additional driver-level validation beyond binary resolution.
Currently a no-op (returns `nil`), matching the QEMU plugin's pattern. The
binary path is already validated by `exec.LookPath` in `Builder.Run()` before
the driver is created. This method exists as an extension point for future
validation (e.g. checking SIMH version compatibility).

### `SimhDriver.Version() (string, error)`

Best-effort version detection. SIMH simulators do not have a consistent
`--version` flag. The recommended approach:

1. Run `<binary> --help` and capture stderr/stdout.
2. Attempt to parse a version string from the output using a regex.
3. If parsing fails (or the command fails), return `("unknown", nil)` — no
   error. Version detection is informational only and is logged for debugging.
   It is **not** used for any decision-making in the plugin.

This method is not called in any critical path. It exists for logging/debugging
purposes and may be called once at the start of `Run()` after driver creation.

### Mock Driver

Provide a `MockDriver` implementing the `Driver` interface for unit tests.
Each method records calls and returns configurable results.

## 8. Multistep Sequence (`Builder.Run()`)

The `Run()` method first resolves the SIMH binary and creates a driver:

1. Call `exec.LookPath(config.SimhBinary)` to resolve the binary path.
2. Create a `SimhDriver` with the resolved path.
3. Call `driver.Verify()` for any additional validation.
4. If any of these fail, return an error immediately (before any steps run).

Then it assembles steps in this exact order:

| # | Step | Condition | Description |
|---|------|-----------|-------------|
| 1 | `commonsteps.StepDownload` | `iso_url`/`iso_urls` configured | Download the disk/tape image to the Packer cache directory. Store path in state as `iso_path`. |
| 2 | `stepPrepareOutputDir` | always | Create `output_directory`. Remove first if `--force`. |
| 3 | `commonsteps.HTTPServerFromHTTPConfig` | always | Start the built-in HTTP server (no-op if `http_directory`/`http_content` not set). Stores `http_port` in state. |
| 4 | `stepDiscoverHTTPIP` | always | Determine the IP the guest should use to reach the HTTP server. Stores `http_ip` in state. |
| 5 | `communicator.StepSSHKeyGen` | `communicator == "ssh"` | Generate ephemeral SSH key pair, or load existing key if `ssh_private_key_file` is set. Writes to `communicator.Config.SSHPublicKey` / `SSHPrivateKey` fields. |
| 6 | `stepForwardPort` | `communicator != "none"` and `!skip_port_forward` | Find an available host port in `[host_port_min, host_port_max]`. Store in state as `commHostPort`. |
| 7 | `stepConfigureConsole` | always | Find an available Telnet port for the simulated console, store in state as `console_port`. |
| 8 | `stepCreateCommandFile` | always | Generate the SIMH command file (see §9). Store path in state as `command_file_path`. |
| 9 | `stepRun` | always | Launch the SIMH process with the command file. |
| 10 | `stepBootCommand` | `boot_steps` is non-empty | Wait `boot_wait`, connect to the console telnet port, execute boot steps (expect/send). See §10.8. |
| 11 | `communicator.StepConnect` | always | Establish communicator connection. When type is `"ssh"`, connects to the guest. When type is `"none"`, places a no-op stub communicator in state. (See note below.) |
| 12 | `commonsteps.StepProvision` | always | Run Packer provisioners via the Hook. (See note below.) |
| 13 | `commonsteps.StepCleanupTempKeys` | `communicator == "ssh"` | Remove temporary SSH keys from the guest. |
| 14 | `stepShutdown` | always | Wait for the SIMH process to exit (up to `shutdown_timeout`). Kill on timeout. |

Use `multistep.If(condition, step)` for conditional steps.

**Step ordering note**: `StepDownload` (step 1) runs **before**
`stepPrepareOutputDir` (step 2), matching the QEMU plugin's ordering.
`StepDownload` downloads to the Packer cache directory (not
`output_directory`), so the output directory does not need to exist yet.
Users should **not** set `iso_target_path` to a path under
`output_directory`, as the directory won't exist when the download runs.

**`StepConnect` and `StepProvision` with communicator `"none"`**: Both steps
run unconditionally (matching the QEMU plugin's pattern — QEMU does NOT wrap
`StepConnect` in `multistep.If`). When the communicator is `"none"`:

1. **`StepConnect`** detects the `"none"` type, creates a `none.comm` stub
   communicator, stores it in state under `"communicator"`, and returns
   `ActionContinue`. It does **not** store `"communicator_config"` in state
   (it returns before that line).
2. **`StepProvision`** finds the `none.comm` stub in state and passes it to
   provisioners. If no provisioners are defined, this is a no-op. If
   provisioners only run commands (e.g. `shell`), they "succeed" silently
   (exit code 0, no actual execution). If provisioners require file transfer
   (`Upload`/`Download`), they **fail** with an error.
3. **`PopulateProvisionHookData`** logs a warning about missing
   `"communicator_config"` but does not error.

This design ensures `StepProvision` always has a valid communicator in state,
avoiding nil pointer panics.

**Provisioner hook data**: `PopulateProvisionHookData()` is called internally
by `StepProvision` (inside `runWithHook()`). The builder does **not** need to
call it explicitly — this matches the QEMU plugin, which simply does
`new(commonsteps.StepProvision)`. The function reads `"http_ip"`,
`"http_port"`, and `"communicator_config"` from the state bag to populate
template data for provisioners (`PackerHTTPIP`, `PackerHTTPPort`, `Host`,
`Port`, `SSHPublicKey`, etc.).

### State Bag Keys

| Key | Type | Set by | Description |
|-----|------|--------|-------------|
| `config` | `*Config` | `Run()` | Builder configuration. |
| `debug` | `bool` | `Run()` | Whether `--debug` was passed. |
| `driver` | `Driver` | `Run()` | The SIMH driver instance. |
| `hook` | `packer.Hook` | `Run()` | Packer hook for provisioners. |
| `ui` | `packer.Ui` | `Run()` | Packer UI for output. |
| `iso_path` | `string` | Step 1 | Path to downloaded image file. Only set if ISO download ran. |
| `http_port` | `int` | Step 3 | Port of the HTTP server. `0` if no HTTP content configured. Set by the SDK's `StepHTTPServer`. |
| `http_ip` | `string` | Step 4 | IP the guest should use to reach the HTTP server. Set by `stepDiscoverHTTPIP`. |
| `commHostPort` | `int` | Step 6 | Selected host port for communicator forwarding. Only set if `stepForwardPort` runs. |
| `console_port` | `int` | Step 7 | Telnet console port. |
| `command_file_path` | `string` | Step 8 | Absolute path to the generated command file. |
| `disk_paths` | `[]string` | Step 8 | Resolved absolute paths of all disk attachments. Used for artifact state. |
| `communicator` | `packer.Communicator` | Step 11 | The connected communicator instance. Set by SDK's `StepConnect`. |
| `communicator_config` | `*communicator.Config` | Step 11 | Communicator config. Set by SDK's `StepConnect`. Used by `PopulateProvisionHookData` to read `SSHPublicKey`, `SSHPrivateKey`, etc. |
| `generated_data` | `map[string]interface{}` | Step 12 | Data from provisioners. |

### Artifact Collection

After all steps complete successfully, `Run()`:

1. Walks `output_directory` collecting all regular files.
2. **Excludes** the following files from the artifact:
   - `<vm_name>.simh` (the generated command file)
   - `<vm_name>.console.log` (the console log, if any)
3. All remaining files are included in the artifact. This includes disk images,
   tape images, ROM files, and any other files SIMH created during the build.
4. Returns an `Artifact` with the collected file paths and metadata.

**Rationale**: Rather than filtering by extension (which would require
maintaining a list of SIMH disk/tape extensions that varies by simulator),
the plugin excludes the known generated metadata files and includes everything
else. This is safe because `output_directory` is created fresh for each build.

### Output Directory Lifecycle

| Event | Behaviour |
|-------|-----------|
| `Prepare()` | **Validate only.** If `output_directory` exists and `packer_force` is false, return an error. Do not modify the filesystem. |
| `stepPrepareOutputDir.Run()` | If `packer_force` and directory exists, `os.RemoveAll()` then `os.MkdirAll()`. Otherwise `os.MkdirAll()`. |
| `stepPrepareOutputDir.Cleanup()` | If the build **failed or was cancelled** AND `packer_debug` is **false**, remove `output_directory`. If `packer_debug` is true, leave the directory intact for post-mortem inspection. |
| Successful build | Directory and artifact files are preserved. |

## 9. Command File Generation (`stepCreateCommandFile`)

This is the most important step. It generates a SIMH command file by assembling
commands in a specific order.

### 9.1 Runtime Interpolation

Before writing any command to the file, `stepCreateCommandFile` performs Pass 2
interpolation. It:

1. Populates a `templateData` struct from the state bag (see §5.4).
2. Sets `config.ctx.Data = &templateData{...}`.
3. For every string that was excluded from Pass 1 interpolation, calls
   `interpolate.Render(str, &config.ctx)`.

This ensures that both Packer built-in functions (`{{ user }}`, `{{ env }}`,
etc.) **and** runtime variables (`{{ .ISOPath }}`, `{{ .HostPort }}`, etc.) are
resolved.

### 9.2 Path Handling

- **Relative paths** in `disk_attachments[].path`: After interpolation, if the
  path is not absolute, it is joined with the absolute path of
  `output_directory` using `filepath.Join()`.
- **Parent directory creation**: For each disk attachment path that is
  **relative** (or under `output_directory` after resolution), the plugin
  calls `os.MkdirAll(filepath.Dir(resolvedPath), 0755)` to ensure parent
  directories exist (e.g. `{{ .OutputDir }}/disks/system.dsk`). For
  **absolute paths outside `output_directory`**, the plugin does **not**
  attempt to create parent directories — the path is assumed to already exist.
  If it doesn't, SIMH's ATTACH command will fail and the error will appear in
  the Packer log.
- **Quoting**: Paths containing whitespace are **quoted with double quotes** in
  the generated SIMH commands: `ATTACH RQ0 "path with spaces/disk.dsk"`.
  Paths without whitespace are written unquoted. The quoting rule: if
  `strings.ContainsAny(path, " \t")`, wrap in `"..."`. Paths containing
  literal double-quote characters (`"`) are **rejected with a validation
  error** during `stepCreateCommandFile` — SIMH's command parser does not
  support escaped quotes within quoted strings, so such paths cannot be
  represented safely.

### 9.3 If `command_file` is set (external command file)

1. Start with the header comment:
   `; Generated by packer-plugin-simh — do not edit`.
2. Insert `SET CONSOLE TELNET=BUFFERED=<console_bind_address>:<console_port>`
   (and optionally `SET CONSOLE LOG=<path>`) **after** the header and
   **before** the interpolated file content.
3. Read the external file contents.
4. Apply Pass 2 interpolation to the entire file content as a single template
   string.
5. Append `QUIT` as the very last line.
6. Write the combined content to `<output_directory>/<vm_name>.simh`.
7. Store the absolute path in state as `command_file_path`.

**Ordering**: console config → external file content → QUIT.

**Structured fields when `command_file` is set**: The fields `cpu_type`,
`memory`, `cpu_options`, `disk_attachments`, `network_device`,
`network_commands`, and `simh_args` are **silently ignored** when
`command_file` is set. The external file is assumed to handle all device
configuration. The following fields **still apply** on top of the external
file:

- Console telnet configuration — always prepended before file content.
- `console_log` — controls whether `SET CONSOLE LOG=<path>` is emitted.
- `boot_steps` — executed at runtime via the telnet console (not in the
  command file).

### 9.4 If `command_file` is not set (generated command file)

Generate the file `<output_directory>/<vm_name>.simh` with commands in this
order:

#### Section 1 — Header

```
; Generated by packer-plugin-simh — do not edit
```

#### Section 2 — Console Configuration

Always emitted. The console telnet port is required for `stepBootCommand` to
interact with the simulated machine.

```
; Console configuration
SET CONSOLE TELNET=BUFFERED=<console_bind_address>:<console_port>
SET CONSOLE LOG=<output_directory>/<vm_name>.console.log   ; if console_log is true
```

The `BUFFERED` keyword is critical: it allows the simulator to run without a
connected telnet client. Console output is buffered internally and replayed
when a client connects. Without `BUFFERED`, SIMH would block at boot waiting
for a telnet connection.

SIMH supports `address:port` syntax for `SET CONSOLE TELNET=`. If
`console_bind_address` is `"127.0.0.1"` (the default), the console is only
accessible from localhost. If set to `"0.0.0.0"`, it listens on all
interfaces.

The log path is quoted if it contains spaces.

#### Section 3 — CPU Configuration

Only emit if at least one CPU field is non-empty:

```
; CPU configuration
SET CPU <cpu_type>            ; if cpu_type is non-empty
SET CPU <memory>              ; if memory is non-empty
SET CPU <cpu_options[0]>      ; for each cpu_options entry
SET CPU <cpu_options[1]>
...
```

#### Section 4 — Extra SIMH Commands

Only emit if `simh_args` is non-empty. Each entry is interpolated:

```
; Additional SIMH commands
<interpolated simh_args[0]>
<interpolated simh_args[1]>
...
```

#### Section 5 — Network Configuration

Only emit if `network_device` is set or `network_commands` is non-empty:

```
; Network configuration
SET <network_device.device> MAC=<mac>             ; if mac is set
SET <network_device.device> <set_commands[0]>     ; for each set_command
...
ATTACH <network_device.device> <interpolated attach_type>
<interpolated network_commands[0]>                ; raw network commands
<interpolated network_commands[1]>
...
```

#### Section 6 — Disk Attachments

For each entry in `disk_attachments`:

```
; Disk: <device>
SET <device> <set_commands[0]>     ; for each set_command
SET <device> <set_commands[1]>
...
ATTACH <device> <resolved_and_quoted_path> <options>
```

#### Section 7 — Boot Command

The `BOOT` SCP command that starts the simulated processor. This is always
the last command before `QUIT` in the generated command file. The `BOOT`
command is **blocking** — it enters the simulator run loop and does not
return to the SCP until the simulated CPU halts (e.g. after OS shutdown or
a `HALT` instruction).

```
; Boot
BOOT CPU
```

**Note**: The `BOOT CPU` command is currently hardcoded. A future version may
allow configuring the boot device/command. For now, users requiring a
different boot command (e.g. `BOOT RQ0`) should use the `command_file` option
to provide their own command file.

#### Section 8 — Quit

```
; Auto quit
QUIT
```

`QUIT` is always appended as the very last line. When the simulated CPU
halts, control returns to the SCP and `QUIT` executes, causing SIMH to exit
cleanly.

**Note**: `QUIT`, `EXIT`, and `BYE` are synonyms in SIMH. All cause the
simulator to terminate. The plugin uses `QUIT`. When SIMH exits via `QUIT`,
it automatically detaches all devices.

### 9.5 Final Notes

- The file must end with a newline.
- The step logs the full path to the generated command file via `ui.Say()`.
- In debug mode (`packer_debug`), the step also logs the full contents of the
  generated command file via `ui.Say()`.

## 10. Step Implementations

**Error propagation convention**: Every custom step that returns `ActionHalt`
due to an error **must** call `state.Put("error", err)` before returning.
This is a hard rule for all steps defined by this plugin. SDK steps
(`StepDownload`, `StepHTTPServer`, `StepConnect`, `StepProvision`, etc.)
follow this convention internally — they set `"error"` in state before
halting.

`stepPrepareOutputDir.Cleanup()` checks for build failure using **both**:

```go
_, halted := state.GetOk(multistep.StateHalted)
_, cancelled := state.GetOk(multistep.StateCancelled)
if (halted || cancelled) && !config.PackerDebug {
    // remove output directory
}
```

This catches failures from both custom and SDK steps, as well as user
cancellation (Ctrl+C). The `multistep.StateHalted` key is set automatically
by the SDK runner when any step returns `ActionHalt`, regardless of whether
`"error"` was also set. This is more robust than checking `"error"` alone.

### 10.1 `stepPrepareOutputDir`

- **Run**: If `packer_force` is set and `output_directory` exists, call
  `os.RemoveAll(dir)`. Then call `os.MkdirAll(dir, 0755)`.
- **Cleanup**: If the multistep runner's state contains
  `multistep.StateHalted` or `multistep.StateCancelled`, **and**
  `packer_debug` is false, remove `output_directory` via `os.RemoveAll()`. If
  `packer_debug` is true, log a message:
  `"Leaving output directory for debug inspection: <dir>"` and do **not**
  delete. On successful builds (neither halted nor cancelled), do nothing —
  the directory and its contents are the build artifact.

### 10.2 `stepDiscoverHTTPIP`

Determines the IP address the guest should use to reach Packer's HTTP server.

- **Run**:
  1. If `config.HTTPIP` (the `http_ip` config field) is non-empty, use that
     value directly.
  2. Otherwise, if `network_device` is configured and `attach_type` starts
     with `"nat:"` (case-insensitive prefix match on the **raw,
     un-interpolated** string), use `"10.0.2.2"` (SIMH's NAT gateway IP,
     matching QEMU's SLIRP convention).
  3. Otherwise, use `"127.0.0.1"`.
  4. Store the result in state as `"http_ip"`.
- **Cleanup**: No-op.

**Note on un-interpolated matching**: This step runs before
`stepCreateCommandFile` (which performs Pass 2 interpolation), so
`attach_type` still contains raw template expressions like
`"nat:tcp={{ .HostPort }}:10.0.2.15:22"`. The `"nat:"` prefix check works
correctly on this raw string. However, if a user writes something like
`attach_type = "{{ env \"NET_TYPE\" }}:tcp=..."`, the prefix check would not
detect NAT and would fall through to `"127.0.0.1"`. In such cases, the user
should set the `http_ip` config field explicitly.

**Note**: The SDK's `StepHTTPServer` only stores `"http_port"` in the state
bag. It does **not** store `"http_ip"`. The builder is responsible for
determining and storing `"http_ip"`, which is consumed by
`PopulateProvisionHookData()` to set `PackerHTTPIP` / `PACKER_HTTP_IP` for
provisioners. Without this step, provisioners would see
`"ERR_HTTP_IP_NOT_IMPLEMENTED_BY_BUILDER"`.

### 10.3 `stepConfigureConsole`

- **Run**: Iterate ports from `console_port_min` to `console_port_max`,
  attempt `net.Listen("tcp", "<console_bind_address>:<port>")` to find an
  available port. Close the listener immediately. Store the port in state as
  `console_port`. The generated command file will use
  `SET CONSOLE TELNET=BUFFERED=<console_bind_address>:<port>` (SIMH supports
  the `address:port` syntax). Log via `ui.Say()`:
  `"SIMH console will be available at telnet://<console_bind_address>:<port>"`.
- **Cleanup**: No-op.

### 10.4 `stepCreateCommandFile`

See §9 above for the full command file generation logic.

- **Run**: Populate `templateData` from state, generate or load the command
  file, create parent directories for disk attachment paths, write the command
  file to disk, store absolute path in state as `command_file_path`.
- **Cleanup**: No-op (the output dir cleanup handles file removal).

### 10.5 `stepForwardPort`

Selects an available host port for the SSH communicator.

- **Run**: If `communicator == "none"` or `skip_port_forward == true`, skip
  (return `ActionContinue`). Otherwise, iterate ports from `host_port_min` to
  `host_port_max`, attempt `net.Listen("tcp", "127.0.0.1:<port>")` to find
  an available port. Close the listener immediately. Store in state as
  `commHostPort`. Log via `ui.Say()`:
  `"Selected host port <port> for communicator forwarding"`.
- **Cleanup**: No-op.

**How the port is used**: The `{{ .HostPort }}` template variable makes this
port available in `network_device.attach_type` and `network_commands`. The user
is responsible for configuring SIMH's network to forward from this host port to
the guest's communicator port. For example:

```hcl
network_device {
  device      = "XQ"
  attach_type = "nat:tcp={{ .HostPort }}:10.0.2.15:{{ .GuestPort }}"
}
```

The plugin itself does not configure NAT forwarding — it provides the port
number; the user's SIMH network configuration consumes it.

### 10.6 `stepRun`

- **Run**: Retrieve `command_file_path` and `driver` from state. Call
  `driver.Simh(commandFilePath)`. If it returns an error, set `"error"` in
  state and return `ActionHalt`.
- **Cleanup**: Call `driver.Stop()` to kill the SIMH process if still running.

### 10.7 `stepShutdown`

- **Run**: Create a timeout context from `shutdown_timeout`. Call
  `driver.WaitForShutdown(ctx.Done())`.
  - If it returns `true` (process exited on its own): log success, return
    `ActionContinue`.
  - If it returns `false` (timeout): call `driver.Stop()`, log an error
    (`"SIMH did not exit within timeout; process killed"`), set `"error"` in
    state, and return `ActionHalt`. This **fails the build**.
  - If the parent context is cancelled (user interrupt): call `driver.Stop()`,
    return `ActionHalt`.
- **Cleanup**: No-op.

**Rationale**: A timeout typically indicates that the simulated CPU never
halted (e.g. the OS never shut down, or boot_steps did not complete the
expected sequence). Silently succeeding would produce potentially incomplete
or corrupt disk images. Failing the build makes the error visible. The
`stepPrepareOutputDir` cleanup will preserve the output directory if
`packer_debug` is true, allowing post-mortem inspection.

### 10.8 `stepBootCommand`

Connects to the simulated console via telnet and executes boot steps. This is
the primary mechanism for interactive guest communication during the build.

- **Run**:
  1. If `boot_steps` is empty, skip (return `ActionContinue`).
  2. Wait `boot_wait` duration. This gives SIMH time to start, initialise
     devices, and begin listening on the console telnet port.
  3. Retrieve `console_port` from state.
  4. Establish a TCP connection to
     `<console_bind_address>:<console_port>`. Retry the connection with
     exponential backoff for up to 30 seconds if SIMH has not started
     listening yet. If the connection cannot be established, set `"error"`
     in state and return `ActionHalt`.
  5. Perform a `templateData` struct from the state bag (same as
     `stepCreateCommandFile`), set `config.ctx.Data = &templateData{...}`.
  6. Create a `telnetDriver` wrapping the TCP connection (see §10.9).
  7. For each `[expect, send, description]` in `boot_steps`:
     a. Log via `ui.Say()`: `"Boot step: <description>"`.
     b. Interpolate the `expect` string using `interpolate.Render()`.
     c. If `expect` is non-empty after interpolation:
        - Read from the telnet connection, appending to an internal buffer.
        - After each read, check if the buffer contains the `expect`
          substring (using `strings.Contains`).
        - If `boot_step_timeout` expires before the pattern is found, log
          the error (including the last ~500 bytes of console output for
          debugging), set `"error"` in state, and return `ActionHalt`.
     d. Interpolate the `send` string using `interpolate.Render()`.
     e. Parse the send string via
        `bootcommand.GenerateExpressionSequence(send)`.
     f. Execute the expression sequence via `seq.Do(ctx, telnetDriver)`.
        This sends characters/special keys to the console.
     g. Log via `ui.Message()` (in debug mode): the matched output and sent
        text.
  8. Close the telnet connection.
  9. Return `ActionContinue`.

- **Cleanup**: Close the telnet connection if still open.

**Console output buffer**: The step maintains a single `bytes.Buffer` that
accumulates all console output read during the step. The buffer is **not**
cleared between boot steps — this is intentional. Output from a previous
step may contain the pattern for the next step (e.g. if the guest produces
output faster than the plugin reads it). The `strings.Contains` check on
the full buffer ensures patterns are not missed due to read boundaries.

**Telnet protocol handling**: SIMH's telnet console uses the standard telnet
protocol (RFC 854). The plugin must handle telnet IAC (Interpret As Command)
sequences. The simplest approach is to use a telnet library or strip IAC
sequences manually. SIMH's console telnet is straightforward — it primarily
uses IAC for initial option negotiation (WILL/WONT/DO/DONT for ECHO,
SUPPRESS-GO-AHEAD, etc.). After negotiation, the connection carries raw
character data. The plugin should reject all telnet options (respond WONT/DONT
to all requests) to keep the connection in its simplest mode.

**Cancellation**: The step monitors the multistep runner's cancel channel.
If the build is cancelled (e.g. Ctrl+C), the step closes the telnet
connection and returns `ActionHalt`.

### 10.9 `telnetDriver` (`console_driver.go`)

The `telnetDriver` implements the Packer SDK's `bootcommand.BCDriver`
interface, sending keystrokes to the simulated console over the telnet
connection.

```go
type telnetDriver struct {
    conn     net.Conn
    interval time.Duration // boot_key_interval
}
```

#### `SendKey(key rune, action KeyAction) error`

- If `action` is `KeyOn` or `KeyOff`: no-op (return nil). Text terminals
  do not have separate key-press/key-release events.
- If `action` is `KeyPress`: write the UTF-8 encoding of `key` to `conn`.
  Sleep `interval` after writing.

#### `SendSpecial(special string, action KeyAction) error`

- If `action` is `KeyOn` or `KeyOff`: no-op (return nil).
- If `action` is `KeyPress`: map the special key name to its text terminal
  equivalent and write to `conn`. Sleep `interval` after writing.

Special key mapping:

| SDK special key | Text terminal output | Notes |
|-----------------|---------------------|-------|
| `enter`, `return` | `\r` | Carriage return |
| `tab` | `\t` (`\x09`) | |
| `bs` | `\x08` | Backspace |
| `del` | `\x7f` | Delete |
| `esc` | `\x1b` | Escape |
| `spacebar` | `\x20` | Space |
| `up` | `\x1b[A` | ANSI escape |
| `down` | `\x1b[B` | ANSI escape |
| `right` | `\x1b[C` | ANSI escape |
| `left` | `\x1b[D` | ANSI escape |
| `insert` | `\x1b[2~` | ANSI escape |
| `home` | `\x1b[H` | ANSI escape |
| `end` | `\x1b[F` | ANSI escape |
| `pageUp` | `\x1b[5~` | ANSI escape |
| `pageDown` | `\x1b[6~` | ANSI escape |
| `f1`..`f12` | ANSI F-key sequences | `\x1bOP`..`\x1b[24~` |
| `leftCtrl`+char | Control character | See note below |
| `leftAlt`+char | `\x1b` + char | Meta/Alt prefix |
| All other modifiers (`rightCtrl`, `leftShift`, `rightShift`, `leftSuper`, `rightSuper`, `menu`) | No-op | Not meaningful for text terminals |

**Modifier keys**: The SDK's boot command syntax supports modifier toggles
like `<leftCtrlOn>c<leftCtrlOff>` to produce Ctrl+C. The `telnetDriver`
handles this by tracking modifier state:

- When `SendSpecial("leftCtrl", KeyOn)` is called, set an internal
  `ctrlHeld = true` flag.
- When `SendKey('c', KeyPress)` is called while `ctrlHeld` is true, send
  `\x03` (Ctrl+C = `rune - 0x60`) instead of `'c'`.
- When `SendSpecial("leftCtrl", KeyOff)` is called, clear the flag.

Similarly for `leftAlt`: when held, prepend `\x1b` before the character
(Meta/Alt sends ESC + char on most terminals).

#### `Flush() error`

No-op (return nil). The telnet connection is unbuffered — each write goes
directly to the network.

## 12. SSH / Communicator Helpers (`ssh.go`)

### `commHost(host string) func(multistep.StateBag) (string, error)`

Returns a closure that:
1. Returns `host` if the user set `comm_host` to a non-empty value.
2. Falls back to `"127.0.0.1"`.

### `commPort(commConfig *communicator.Config) func(multistep.StateBag) (int, error)`

Returns a closure that captures `commConfig` and:
1. If `commHostPort` exists in state (set by `stepForwardPort`), return it.
2. Otherwise, return `commConfig.Port()` (defaults to 22 for SSH).

The closure signature matches what `StepConnect.SSHPort` expects:
`func(multistep.StateBag) (int, error)`.

These functions are passed to `communicator.StepConnect`:

```go
&communicator.StepConnect{
    Config:    &config.Comm,
    Host:      commHost(config.CommHost),
    SSHConfig: config.Comm.SSHConfigFunc(),
    SSHPort:   commPort(&config.Comm),
}
```

### SSH Key Access

`StepSSHKeyGen` is wrapped in `multistep.If(comm.Type == "ssh", ...)` — it
only runs when the communicator is SSH. The condition checks **only** the
communicator type, not whether a key is already provided. However, the step
itself handles existing keys:

- If `ssh_private_key_file` is set: the step reads the file and derives the
  public key. No new key is generated.
- If `ssh_private_key_file` is empty: the step generates a new ephemeral key
  pair using the configured algorithm (`ssh_temporary_key_pair_type`,
  default RSA).

In both cases, the step writes to `communicator.Config.SSHPublicKey` and
`SSHPrivateKey` (as `[]byte`), **not** to the state bag. The
`stepCreateCommandFile` reads `string(config.Comm.SSHPublicKey)` to populate
`templateData.SSHPublicKey`.

Later, `StepConnect` stores the `communicator.Config` in state as
`"communicator_config"`. `PopulateProvisionHookData()` reads it from there to
expose `SSHPublicKey`, `SSHPrivateKey`, etc. to provisioners.

## 14. Testing Strategy

### 14.1 Unit Tests

Each step should have its own `_test.go` file. Tests use a `MockDriver` and a
`multistep.BasicStateBag` pre-populated with expected state.

Key test scenarios:

| Component | Tests |
|-----------|-------|
| `Config.Prepare()` | Valid defaults, missing required fields, invalid port ranges, `output_directory` exists without force, disk attachment validation, boot_steps format validation (3-element tuples), ISO fields optional, excluded fields not interpolated in Pass 1 |
| `Builder.Run()` / `newDriver()` | `simh_binary` not found via `exec.LookPath`, `Driver.Verify()` failure |
| `stepCreateCommandFile` | Generated command file content matches expected output for various config combinations: CPU-only, disks, network, console, external command file (ordering: console → file content → QUIT), template interpolation (verify `{{ .ISOPath }}`, `{{ .HostPort }}`, `{{ .HTTPIP }}` etc. are resolved), path quoting for spaces, path with `"` rejected, relative path resolution, absolute paths outside output_dir (no MkdirAll), QUIT always appended, structured fields silently ignored when command_file is set |
| `stepPrepareOutputDir` | Creates directory, removes on force, cleans up on error (not on debug), does not clean up on success |
| `stepDiscoverHTTPIP` | Returns user override, NAT default, fallback default |
| `stepForwardPort` | Port selection, skip when communicator is none, skip when skip_port_forward is true |
| `stepConfigureConsole` | Port selection within range |
| `stepRun` | Calls `driver.Simh()` with correct path, handles launch errors |
| `stepBootCommand` | Expect/send over mock telnet connection: empty expect sends immediately, non-empty expect waits for pattern match, timeout on unmatched pattern, template interpolation of expect/send strings, SDK boot command syntax parsed correctly, cancellation handling |
| `telnetDriver` | `SendKey` writes character, `SendSpecial` maps to correct escape sequences, modifier state tracking (Ctrl+char → control character), `KeyOn`/`KeyOff` no-ops for unsupported modifiers |
| `stepShutdown` | Waits for exit, kills on timeout and fails build, handles cancellation |
| `Artifact` | `Files()` excludes command file and console log, `Destroy()`, `BuilderId()` |
| `Driver` | `Simh()` starts process, early exit code 0 is success, early exit non-zero is error, `Stop()` kills, `WaitForShutdown()` blocks |

### 14.2 Acceptance Tests

Use the SDK's `acctest` package. Require a real SIMH binary on `$PATH`. Gate
acceptance tests behind `ACC_TEST_SIMH_BINARY` environment variable (set to
the binary name, e.g. `vax`).

**Minimal acceptance test** — a VAX simulator that immediately quits (no ROMs
or disk images required):

```hcl
source "simh" "acc-test" {
  simh_binary      = "vax"
  output_directory = "output-acc-test"
  vm_name          = "acc-test"
  communicator     = "none"
  # No boot_steps — the command file will BOOT CPU then QUIT when it halts.
  shutdown_timeout = "30s"
}

build {
  sources = ["source.simh.acc-test"]
}
```

This generates a command file containing console configuration, `BOOT CPU`,
and `QUIT`. The VAX simulator starts, boots, halts (no ROMs loaded), and
QUIT executes. The test verifies:
1. The output directory was created.
2. The command file (`acc-test.simh`) was generated.
3. The builder returned a valid artifact.
4. No errors occurred.

This test requires only the `vax` binary on `$PATH` — no ROM files, disk
images, or network configuration. Most SIMH simulators can be started and
immediately quit without additional dependencies.

   a. `stepPrepareOutputDir`
   b. `stepDiscoverHTTPIP`

7. **Builder** — `builder.go` wiring everything together.
8. **Unit tests** for each component.
9. **Acceptance tests**.
10. **Documentation and examples**.

## 17. Design Notes

- **Disk creation**: Unlike QEMU which has `qemu-img create` to create blank
  disk images, SIMH creates disk files on first `ATTACH` if they don't exist
  (for most device types). The plugin does not need a separate disk creation
  step. If a specific disk size or format is needed, the user can use
  `simh_args` to issue the appropriate SIMH commands or pre-create the image
  externally.

- **SIMH process output**: The `SimhDriver.Simh()` method captures stdout and
  stderr from the SIMH process and forwards each line through Go's `log`
  package (which Packer routes to its log output, visible with
  `PACKER_LOG=1`). This matches the QEMU plugin's approach.

- **No VNC**: This plugin does not use VNC or any graphical protocol. Unlike
  the QEMU plugin which sends keystrokes over VNC, this plugin sends
  keystrokes to SIMH's simulated console via a telnet connection. The SDK's
  `bootcommand` package **is** used — specifically the expression parser
  (`GenerateExpressionSequence`) and the `BCDriver` interface — but with a
  custom `telnetDriver` implementation instead of the SDK's VNC driver. The
  `telnetDriver` sends text characters and escape sequences rather than
  keyboard scancodes.

- **Telnet console interaction**: SIMH's `SET CONSOLE TELNET=BUFFERED=<port>`
  exposes the simulated machine's console (what the guest OS sees) as a telnet
  server. The plugin connects to this telnet port to send keystrokes and read
  console output. The `BUFFERED` mode allows SIMH to run without a connected
  client — output is stored internally and replayed when the plugin connects.
  This is the mechanism used for `boot_steps` (expect/send pairs). The
  command file handles device configuration and boots the CPU; `boot_steps`
  handles the interactive guest prompts (VMB, login, etc.) via telnet.

- **Communicator flexibility**: The plugin supports `ssh` and `none`
  communicator types. **WinRM is not supported** — historical systems
  simulated by SIMH do not run Windows. `Prepare()` returns an error if
  `communicator = "winrm"` is set. Both `StepConnect` and `StepProvision` run
  unconditionally (matching the QEMU plugin). When communicator is `none`,
  `StepConnect` places a no-op stub communicator in state; provisioners that
  only run commands will silently succeed, while provisioners requiring file
  transfer will fail (see §8 for details). The user is responsible for
  ensuring network connectivity between the host and guest when using `ssh`
  (typically via SIMH's NAT or bridged networking).

- **Two interfaces to SIMH**: The plugin uses two distinct interfaces:
  1. **Command file** — controls device configuration, CPU setup, network
     attachments, and the `BOOT` command. This is a static script executed
     by SIMH at startup. The command file always ends with `QUIT`.
  2. **Telnet console** — enables interactive communication with the
     simulated machine (boot prompts, OS login, etc.) via `boot_steps`.
     This is a runtime connection established after SIMH starts.

- **SIMH exits via QUIT**: The command file always appends `QUIT` as the last
  line. After `BOOT CPU`, SIMH enters the simulator run loop and blocks at
  the `BOOT` command until the simulated CPU halts. When the CPU halts (e.g.
  after OS shutdown), control returns to the SCP and `QUIT` executes, causing
  SIMH to exit cleanly. If the CPU never halts, `stepShutdown` kills the
  process after `shutdown_timeout`.

- **Port forwarding is user-configured**: The plugin selects an available host
  port but does not itself configure NAT rules. It provides `{{ .HostPort }}`
  and `{{ .GuestPort }}` template variables for the user to embed in their
  SIMH network configuration (e.g. `attach_type`). This keeps the plugin
  generic across different SIMH networking backends.

- **Console portability**: `SET CONSOLE TELNET` and `SET CONSOLE LOG` are
  standard SCP commands. If a particular SIMH build does not support them, the
  command file execution will fail and the error will appear in the Packer log.
  The plugin does not attempt to probe SIMH capabilities.
